The opportunity report lists the properties an agent identity must have
(temporary, derived from a person, attenuable, recorded, revocable, compatible
with ank as it is) and five candidate technologies. This document turns that
list into a design with named parts, so that phase 2 can be specified as
tasks. Section 7 lists what is still to decide; nothing there blocks phase 1.

## 1. What an identity is

An identity is the typed string ank already uses (`human:<name>`,
`<producer>/<version>+<session>`, `process:<name>`), bound to a short-lived
credential the hub can verify. The string stays what the CLI declares and
prints; the credential is what makes a push under that string refusable when
it is not held by its owner. The CLI changes nothing about how it refuses:
refusal on identity happens at the hub, as a refused push
(ADR-38da5a578318 in this corpus).

## 2. The chain of issuance

Three levels, each strictly narrower than the one above:

1. **A person's key.** The same key that signs `accept`. It is the root of
   every agent identity in an organisation and is never held by an agent or
   by the hub.
2. **The organisation's authority on the hub.** The hub operates one
   certificate authority per organisation. Its right to issue is delegated by
   the organisation's registered human keys: a person authorises the
   authority with a signature, the authority issues on their behalf. Issuing a
   credential is not a ratification: ADR-aa5978e70a23 is about `accept`, and
   a credential binds no rule to any code.
3. **Agent credentials.** Issued by the authority to a session, with an
   expiry no later than the work it covers. An orchestrator (herdr-style)
   receives a credential that carries the right to request narrower ones for
   its workers, so a worker's identity traces back through the orchestrator
   to the person, and the orchestrator never holds the person's key.

## 3. The credential

The baseline is a short-lived SSH certificate:

- git already speaks SSH; ank already signs ratifications with SSH keys; the
  hub's SSH front (phase 1) verifies a certificate natively, so phase 2 adds
  no transport.
- The certificate's principal is the identity string. Its extensions carry
  the attenuation: the corpus (`<org>/<corpus>`, ADR-760ba6399bd6), the scope
  globs the holder may claim within, optionally one task id, and the expiry.
- Over HTTP, the same certificate signs a challenge; the bearer token of
  phase 1 remains for organisation-level access only.

Capability tokens with offline attenuation (Biscuit, macaroons) are kept as
the alternative if a later need to attenuate without contacting the hub
appears; phase 2 has none.

## 4. What is checked at push

- The certificate chains to the organisation's authority and is not expired
  or revoked.
- The ref being written is inside the certificate's corpus.
- For a claim: the task's scope lies within the certificate's globs, and the
  claim record's holder equals the certificate's principal.

The last check reads the claim record. ADR-91e5fe9261ba makes claim objects
opaque to the hub and names identity binding as the moment that changes; the
amending ADR decides how the hub reads the holder (a dependency on
`ank-core` once the record format is extracted there, or a minimal reader of
the holder line) and is a prerequisite of phase 2, not of this document.

## 5. Binding to the host

A credential is bound to the session that requested it: the SSH certificate
carries the source constraint the hub can enforce (the connecting host or
network), so a credential copied off a runner is refused elsewhere. Where the
runner cannot offer a stable source, the credential's lifetime is the bound.

## 6. Revocation and the record

- Revocation is a hub action by the organisation (an unsigned human action,
  journaled). It refuses subsequent pushes immediately and expires the live
  leases of that identity through the store, so the event stream carries the
  expiry to every subscribed `watch`. The hub never renews a lease and never
  releases on an agent's behalf; expiring on revocation is the one exception,
  and it is the organisation's act, not the hub's.
- Every accepted push is recorded with the certificate it was made under, in
  the hub's append-only, hash-chained audit log, keyed by the store's sequence
  (ADR-85a8e6f696ea). A proof signed by an identity that has since expired is
  verified years later against that record, not against a live key.

## 7. To decide before phase 2 is specified

1. What the CLI signs beyond the push itself: nothing (the transport
   authenticates), each proof, or each log entry. Each option is an ADR in
   haksolot/ank, since it changes the CLI; none adds a verb.
2. How the hub reads a claim record's holder (the ADR amending
   ADR-91e5fe9261ba).
3. The exact SSH certificate extension names and the HTTP challenge format.
4. Whether `process:ankhub` itself is issued by each organisation's
   authority (so a self-hosted hub's attestations are its own) or by a
   hub-wide one.
