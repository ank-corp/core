Amends ADR-38da5a578318 in one clause: "no change to any verb's refusals"
is dropped. "No new verb" stays, and so does the mechanism: a hub refusal is
a refused push. What changes is what the push carries and what ank does with
it.

Measured on ank 0.9.0 (`crates/ank-cli/src/git.rs`, `push_ref`, and
`crates/ank-cli/src/claim.rs`, `push`): ank writes a ref with
`git push --force-with-lease=<ref>:<expected> origin <object>:<ref>`, one ref
per push. When the push fails it does not read git's output; it runs one
`ls-remote origin <ref>` and classifies by that answer alone:

- `ls-remote` answers: the push is read as a lost compare-and-swap. With a
  witness and an absent ref it is retried once without the witness, then
  reported as lost to nobody. `claim` exits 4.
- `ls-remote` fails: the remote is read as unreachable, and the write is kept
  as **won locally, unsynchronised**. `claim` exits 0 and the agent works.

A hub that refuses a push for a reason ank has no category for (an identity
not held by the pusher, a token outside its scope, a ref outside the
namespace, a corpus the token does not cover) therefore reaches the agent as
one of two false statements: "you lost the race" or "the remote is down, you
hold the task". The second is the dangerous one: it is how a spoofed or
revoked identity keeps working on a task the hub refused it. SPEC-02271880e39c
section 1 ("the CLI changes nothing about how it refuses; refusal on identity
happens at the hub") assumed the first reading was faithful. It is not.

Two halves, one on each side.

**The hub's half (this constraint).** Every refusal is expressed where git
already has a slot for it: the `ng <ref> <reason>` line of receive-pack's
report-status, which `git push` prints as `! [remote rejected] <ref>
(<reason>)`. The reason is a stable token, not prose: `held`, `identity`,
`scope`, `namespace`, `corpus`, `expired`, `revoked`, with the hub's sequence
number where it applies. And a client that may read a corpus keeps reading it:
`ls-remote` and `fetch` on `refs/ank/*` answer even to a client whose push was
just refused, so the client never lands in the "unreachable" branch by
accident. A client with no right to read at all is refused at the transport
(401, 403, SSH key) and ank's "unreachable" reading is then the true one.

**ank's half (decided in haksolot/ank, proposed as haksolot/ank#571, in the same
series as #552, #553 and #554).** ank reads the receive-pack reason and
reports a refused push as what it is: a lost race when the reason is `held`,
a refusal with its reason otherwise, never a local win. The CLI still refuses
on state, never on who is asking; it is the remote that refused on who, and
the CLI reports faithfully. No verb is added. ank is ours, so this is work to
schedule, not a constraint to design around.

What ADR-38da5a578318 keeps: the hub speaks the protocol ank already speaks,
an unmodified ank 0.9 works against it, and a feature that needs a new verb
to be usable belongs in the hub or nowhere. The phase 1 git front implements
the hub's half; nothing in phase 1 depends on ank's half, since phase 1 has
no refusal but `held` and `namespace`.
